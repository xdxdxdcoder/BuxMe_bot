# BuxMe: правила проекта

Этот файл действует только при работе в репозитории BuxMe. Первоисточники: [условия трека «Эффективный бизнес»](docs/hackathon/effective-business.pdf) и [FAQ организаторов](docs/hackathon/faq.pdf). Ниже — рабочая выжимка, а не замена документов. Если решение зависит от формулировки правила, откройте соответствующую страницу PDF и проверьте актуальные правила хакатона и документацию MAX.

## Продукт и MAX

- Решение должно решать конкретную, обоснованную задачу бизнеса в треке «Эффективный бизнес». Определяйте приоритетного пользователя и доводите основной сценарий до результата; не добавляйте функции ради количества (условия, стр. 6–8, 11–13).
- MAX — среда реализации или взаимодействия с продуктом. Основной сценарий должен быть доступен для самостоятельной проверки в MAX, а функциональность — в мобильной и веб-версии MAX. Мини-приложение подключается к выданному чат-боту, а не существует как отдельный от него сервис (условия, стр. 7; FAQ, вопросы 1–3).
- Для мини-приложения нужна публичная HTTPS-ссылка. Её передают организаторам через форму из FAQ для привязки к боту; собственный домен не обязателен. Локальная проверка браузера не заменяет проверку внутри MAX (FAQ, вопросы 2, 3, 17).
- На онлайн-этапе нельзя самостоятельно менять название, ник, логотип или административные настройки выданного бота. Используйте предоставленный токен в разрешённых пределах; если нужна недоступная через API настройка, обратитесь к организаторам (FAQ, вопросы 16, 19).

## Код, данные и безопасность

- Не используйте закрытые библиотеки, частные API или чужой код без разрешения на свободное распространение и использование. Сторонние API должны быть публичными, документированными и допускать выбранный способ использования (условия, стр. 7; FAQ, вопрос 6).
- Не помещайте рабочие токены, пароли, API-ключи и другие секреты в исходный код, репозиторий, примеры конфигурации или тестовые данные (условия, стр. 7, 13).
- Тестовые, синтетические и заранее подготовленные данные допустимы. Явно обозначайте в интерфейсе и материалах, какие данные и интеграции модельные, и что потребуется для реальной интеграции. Не называйте mock-интеграцию работающим подключением (условия, стр. 7–8, 18; FAQ, вопросы 13, 15).
- Для критичных сведений предпочитайте первоисточники, проверяйте актуальность, территорию и применимость. Отделяйте официальные факты от расчётов, рекомендаций, гипотез и модельных данных; не выдавайте вывод генеративной модели за официальный факт (условия, стр. 18).
- AI-инструменты допустимы как помощь при разработке, но команда должна понимать и самостоятельно проверять итоговое решение. Не используйте no-code/low-code как основу конкурсного решения (FAQ, вопросы 8–9).

## Проверка и сдача

- Поддерживайте воспроизводимый запуск через Docker: нужные `Dockerfile`, `compose.yaml`/`docker-compose.yml`, `.dockerignore`, `.env.example` без секретов и файлы с зафиксированными зависимостями. Сборка без первоначальной загрузки базовых образов должна укладываться в пять минут (условия, стр. 9; FAQ, вопрос 7).
- README должен объяснять назначение, основной сценарий, архитектуру, одну команду запуска Docker, окружение, порты, зависимости, интеграции, работу с тестовыми данными, шаги проверки, ожидаемый результат, ограничения, остановку и повторный запуск (условия, стр. 9).
- Если продукт предоставляет собственные HTTP(S)-методы как часть функциональности, для проверки требуются доступный HTTPS-адрес, OpenAPI 3.0/3.1, тестовые данные и доступы, а также `DATA-API.yaml`. Если собственного продуктового API нет, этот файл не нужен. Оценивайте применимость правила по фактическому назначению методов (условия, стр. 10; FAQ, вопрос 12).
- К сдаче нужны работающее решение в MAX, зафиксированная версия кода (репозиторий с commit hash или архив с контрольной суммой) и PDF-презентация с техническим первым слайдом. Рабочие секреты нельзя класть в репозиторий; сведения для проверки передаются предусмотренным организаторами способом (условия, стр. 9–10).
- Срок онлайн-сдачи по FAQ — **30 сентября 2026 года, 12:00 МСК**. После сдачи переданная версия фиксируется; бот должен оставаться доступным на протяжении проверки. Не изменяйте сданную версию после дедлайна, кроме разрешённого организаторами этапа для финалистов (условия, стр. 7, 9; FAQ, вопросы 10–11).

Перед изменениями, затрагивающими интеграцию MAX или сдачу, сверяйтесь с актуальной документацией и историей изменений MAX, а также с официальными правилами хакатона: PDF прямо предупреждает, что документация платформы обновляется (условия, стр. 7, 15).
